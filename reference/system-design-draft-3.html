Prism System Design
System design · draft 3 · working name

Prism

One database. Write once, read in any shape. SQL tables stay the single source of truth; documents, search, cache, vectors and analytics are declared views the database shards, keeps consistent, and can prove correct. Start by attaching to the Postgres you already run, with no migration.

The problem

Every growing product ends up keeping the same data in several places

Teams start on Postgres. As reads get heavy they add MongoDB for nested documents, Elasticsearch for search, Redis for hot keys and, more recently, a vector store for embeddings. Each new store needs a sync pipeline, and each pipeline is a place where data goes missing or stale without anyone noticing.

The core idea

A shape is a view the database keeps up to date for you

You model data once, normalized, in tables. A shape declares another form the same data should be readable in. Prism builds it, shards it alongside its source rows, and updates it incrementally on every write, touching only the rows that changed.

1 · Model once (plain SQL, sharded by customer)
CREATE TABLE customers   (id bigint PRIMARY KEY, name text, tier text);
CREATE TABLE orders      (id bigint, customer_id bigint,
                          placed_at timestamptz, status text);
CREATE TABLE order_items (order_id bigint, customer_id bigint,
                          sku text, qty int, price numeric);
CREATE TABLE products    (sku text PRIMARY KEY, title text,
                          description text);   -- reference table

SELECT prism.distribute('customers', 'orders', 'order_items',
                       by => 'customer_id');
2 · Declare shapes (proposed syntax)
CREATE SHAPE customer_profile AS DOCUMENT
  KEY c.id
  FROM customers c
  NEST orders o ON o.customer_id = c.id
    NEST order_items i ON i.order_id = o.id
  FRESHNESS sync;          -- same shard, same transaction

CREATE SHAPE order_search AS SEARCH
  FROM orders o JOIN customers c ON c.id = o.customer_id
  INDEX (c.name, o.status, o.placed_at)
  FRESHNESS bounded '2s';

CREATE SHAPE product_vectors AS VECTOR
  FROM products p
  EMBED (p.title || ' ' || p.description)
  USING 'any-embedding-model'
  FRESHNESS bounded '30s';  -- re-embeds changed rows only
3 · Read in any shape
// Any MongoDB driver, unchanged application code
db.customer_profile.findOne({ _id: 42 })

// → one document from one shard, no joins at read time
{
  _id: 42, name: "Asha Rao", tier: "gold",
  orders: [
    { id: 9001, status: "shipped",
      items: [ { sku: "KB-01", qty: 1, price: 89.00 } ] }
  ]
}
-- Same data from SQL: GROUP BY and JOIN still work on tables
SELECT c.tier, sum(i.qty * i.price) AS revenue
FROM customers c
JOIN order_items i ON i.customer_id = c.id
GROUP BY c.tier;

-- Search shape, BM25-ranked
SELECT * FROM order_search WHERE order_search @@@ 'asha shipped';

-- Vector shape: "similar products", always current
SELECT sku FROM product_vectors
ORDER BY embedding <=> prism.embed('quiet mechanical keyboard')
LIMIT 10;

The team never writes a sync job. Adding a field to orders flows into every shape that selects it, and editing a product description re-embeds that one product.

What makes it remarkable

Shapes the database builds itself, and proves are right

Draft 2 was a sound assembly. These two capabilities are what turn it into something no competitor can copy quickly. They reinforce each other: the auditor that proves shapes correct is what makes automatically created shapes safe to trust.

Signature one

Proven shapes

Every incremental-view system says it keeps data consistent. None can show it. Prism makes correctness visible at three levels.

  1. A certificate at compile time. The shape compiler derives the incremental form of the query using DBSP's rules, which guarantee the incremental result equals recomputation from scratch. The certificate names the rules used and the assumptions (co-location, freshness tier) it relies on. A shape that cannot be certified is rejected with a reason.
  2. A live auditor in production. A background process samples shape rows, recomputes them from the tables and diffs. The console shows the running count: drift 0 rows · 4.1M checks · 30 days. Any non-zero result pages on-call and pins the offending input.
  3. Public Jepsen results for every release, kept on the website permanently.

Why it sells: database buyers are rightly paranoid. "We can show you" ends the consistency conversation.

Signature two

Automatic shapes

Nobody should have to notice that a query would be faster as a shape. The database notices.

  1. Watch. The proposer reads the query log and groups repeated join-and-nest patterns, the ones an application runs thousands of times a day.
  2. Propose. For each pattern it drafts a shape, estimates its write cost and read speedup from the cost model, and shows both. Accept with one click, or set a policy that auto-accepts below a cost threshold.
  3. Route only when it wins. The planner rewrites a query onto a shape only when a learned model predicts a speedup for that query, and falls back to the tables otherwise. The shape is never on the wrong side of a trade.

Why it sells: for apps built quickly, often by agents, nobody is hand-tuning anything. A database that tunes its own read models is the difference between "works in demo" and "works at scale".

Three more, once the engine exists

  • Time travel. Shapes derive from a log, so customer_profile AS OF '2026-10-07 14:02' rebuilds the document as the tables were then. Debug a ticket or audit a ledger view across documents, search and vectors with one clause.
  • Edge shapes. A shape is already a precomputed, keyed document. Replicating it to edge locations is cheap, and the same freshness token lets an edge read wait for a specific write. Worldwide low-latency reads without a new system.
  • Shapes as API. A keyed shape with auth rules declared beside it is an endpoint: GET /shapes/customer_profile/42. For many apps this removes the backend-for-frontend layer.
Adoption without migration

Attach to the Postgres you already run, then move writes when ready

Asking a team to move its primary database is the slowest sale in infrastructure. Prism starts as a follower instead. Attach is the on-ramp, not the destination: the product only fully pays off once writes move over, but the customer chooses when.

How a request flows · primary mode

Write path and read path

Write: INSERT INTO orders …

  1. Route. The coordinator hashes customer_id and sends the write to the shard that owns that customer.
  2. Sync shapes update in the same transaction. prism_ext recomputes only the affected document in customer_profile. Its rows live on the same shard, so there is no network hop.
  3. Commit. The client gets back a write token: the commit position (LSN) on that shard.
  4. Bounded shapes update right after. The shape engine reads the change from logical replication, computes the delta for order_search, and writes it to the shape's shards. The lag target is set per shape.

Read: findOne({ _id: 42 })

  1. Gateway. The MongoDB wire gateway maps the collection name to the shape customer_profile.
  2. Route by key. _id is the shape key, which is the shard key, so the read goes to exactly one shard.
  3. Freshness check (optional). If the client passed a write token, the shard waits until that position has reached the shape, or returns a clear "not yet" error after a timeout.
  4. Return. One prebuilt BSON document. No joins at read time, which is where the speed of NoSQL comes from.
Consistency model

Two freshness tiers, chosen per shape

Keeping every shape perfectly consistent across shards would make every write a distributed transaction, and writes would crawl. Each shape declares what it needs, and the shape compiler rejects a declaration it cannot honor.

FRESHNESS sync

Same transaction, same shard

The shape updates inside the writing transaction. Readers never see a shape that disagrees with its tables.

Allowed when every source table is co-located on the shape key, or is a small reference table copied to every shard, and Prism is the primary. The compiler checks this.

Cost: slightly slower writes, since each write also does its shape work.

FRESHNESS bounded '2s'

Asynchronous, with a stated lag budget

The shape engine maintains it from the replication stream. Lag is measured continuously and alerts fire when the budget is broken.

Used for shapes that join across shard keys, global aggregates, search over the whole dataset, vector shapes (embedding calls take time), and everything in attach mode.

Read your writes: pass the write token and the read waits for it. In SQL: SET prism.read_after = '…'.

Freshness is reported per read, not per cluster

A cluster-wide "lag: 800ms" number says little about whether this result is current. Following the Vodka work on HTAP freshness, every shape read can return the log position its rows were derived from, so a client or the auditor can state exactly what data a result reflects. The dashboard rolls those up by shape, and alerts fire on the budget each shape declared.

Built-in sharding

Shard by entity, keep joins local, let the advisor catch mistakes

Joins and shards only conflict when the rows being joined live on different machines. Prism takes the approach Citus and Spanner both proved: pick one entity key (customer, tenant, account) and co-locate everything that hangs off it. Most joins then never leave a shard, and SQL keeps working the way people expect.

What the cluster does automatically

  • Co-location. Tables sharing a distribution key land on the same shards, so joins and sync shapes on that key run locally.
  • Reference tables. Small lookup tables (countries, plans, products) are copied to every shard, so joining them is always local.
  • Online rebalancing. Shards move between nodes without downtime when nodes are added or a tenant gets hot.
  • Scatter-gather for the rest. A cross-shard GROUP BY runs in parallel on every shard and merges. Correct, just slower than a local query.

What the shard advisor adds

Choosing the wrong shard key is the most expensive mistake in a sharded database. The advisor reads pg_stat_statements and the shape catalog, and reports:

  • hot queries that cross shards, and the key that would have kept them local
  • tables small enough to become reference tables
  • shapes that could move from bounded to sync if a table were co-located
  • a one-click online reshard plan when a better key is clear
Competitive landscape

Each piece exists somewhere. Nobody ships the combination.

Incremental views alone are a crowded feature: several open source projects and startups keep derived tables fresh. Prism's case rests on putting four things in one product that no competitor combines.

The combination we sell

  • Relational source of truth with full SQL, joins and GROUP BY
  • MongoDB wire compatibility, so document-style apps connect unchanged
  • Shapes maintained across shards, with per-shape freshness and read-your-writes
  • Attach mode, so adoption starts without a migration

Choosing the base

Pick: Postgres 18 + Citus + DocumentDB, with pg_trickle for sync shapes

DocumentDB is Microsoft's MongoDB-compatible Postgres extension, moved to the Linux Foundation in August 2025 under the MIT license. It adds BSON types, document indexes and a Rust gateway that speaks the MongoDB wire protocol, and it ships a distributed mode that shards collections across Citus. That gives us SQL, documents and sharding as working parts today. pg_trickle gives us a head start on in-transaction shape maintenance.

Where it fits

Products whose reads look nothing like their writes

Prism earns its place wherever data is written in normalized form but read as documents, results lists or recommendations. A few typical cases:

Commerce and marketplaces

Orders and inventory stay relational for accounting; storefronts read product documents, catalog search and "similar items" from the same tables.

documentsearchvector

Multi-tenant SaaS

Shard by tenant so every tenant's joins stay local. Per-tenant dashboards and activity feeds read as precomputed shapes, and hot tenants move between nodes online.

cacheanalyticsdocument

Fintech and ledgers

The ledger stays strictly relational and transactional. Statements, balances and customer views are shapes that never drift from the ledger, with read-your-writes after every payment.

documentcache

AI features in existing apps

Retrieval and assistants need embeddings and per-user context that match the database right now. Vector and document shapes keep both current, without a separate embedding pipeline or vector store.

vectordocumentsearch
Research grounding · reviewed October 2026

Recent papers, and the component each one shapes

Each design choice above borrows from published work where it can. The table names the paper, the idea taken, and where it lands in Prism.

PaperIdea we takeWhere it lands
DBSP · VLDB 2023 best paperA mechanical rule that turns any query into its incremental form, with a formal argument that the result equals recomputation.Shape engine; the basis of the compile-time certificate.
Enzyme · Databricks, SIGMOD 2026Incremental maintenance that treats AI and non-deterministic function calls as part of the view, and picks a maintenance strategy per view from a cost model built on plan info and past runs.Vector shapes (embedding calls as view functions); per-shape strategy selection behind the sync/bounded tiers.
Vodka · VLDB 2025Measure freshness against the data a query actually touched, with fine-grained versioning, not against query start time.Per-read freshness reporting; the auditor's definition of "current".
Tailwind · Kraska, Marcus, Yu, 2026A non-invasive planner that rewrites a query onto an accelerator only when a learned model predicts a win, else falls back.Automatic shapes: routing a query to a shape only when it is predicted to be faster.
MVGPT · Alibaba, ICDE 2026A fine-tuned model that forecasts which materialized views a workload will need, deployed in production.The proposer: evidence it works, and a reference design.
AMAZe · 2026A zero-shot multi-agent index advisor: plan, select, combine, revise, reflect.Shard advisor structure.
Drift-Adapter · 2025Upgrading an embedding model without re-encoding the whole corpus.Vector shapes: model upgrades as a supported operation.

Two open problems we would publish on

  • Verified incremental view maintenance. Formal verification in Rust (Verus, Lean pipelines) has reached kernels and cryptography but not database engines. A machine-checked proof that the shape engine's incremental form matches recomputation would be a first, and is what turns the certificate from "derived by rules" into "proven".
  • Learned co-location. No recent work automates shard-key selection from real workloads. The shard advisor's recommendations, with the outcomes of accepted reshards, are the dataset such a paper needs.

Publishing is also hiring: the engineers who can build this read these venues.

Roadmap

Lead with attach mode, earn trust, then become the primary

Each phase gives a customer something usable, and each exit test decides whether the next phase starts. Timings are rough estimates for a small team.

Phase 0 · ~2 months

Attach

  • One image: PG 18 + Citus + DocumentDB + pg_search + pgvector
  • Attach ingest from an existing Postgres
  • Bounded document and search shapes
  • Shapes readable through the MongoDB gateway

Exit: a design partner switches off one MongoDB read model or Elastic sync job.

Phase 1 · ~2 months

Vector shapes

  • CREATE SHAPE … AS VECTOR
  • Re-embed changed rows only, with cost tracking
  • Lag dashboards and alerts per shape

Exit: a partner retires an embedding pipeline or a separate vector store.

Phase 2 · ~3 months

Primary mode

  • Cutover from attach to primary
  • Sync shapes on pg_trickle, sharding-aware
  • Write tokens and per-read freshness; cache shapes
  • Auditor with the public drift counter

Exit: a partner moves production writes onto Prism.

Phase 3 · ~3 months

Scale and cloud

  • Cross-shard shapes on DBSP, with certificates
  • Proposer and predicted-benefit routing
  • Shard advisor and online reshard
  • Managed cloud beta; first Jepsen report

Exit: paying customers on the managed cloud.

After phase 3: time travel, edge shapes, shapes as API, analytics shapes (columnar mirror), live shapes for client sync, event shapes for services, and the verified-IVM research track.

Risks

What could sink this, and what we do about it

Microsoft controls Citus and DocumentDBAzure already runs Cosmos DB for MongoDB vCore on DocumentDB, and can bundle the same parts. Keep sharding behind our own interface, contribute upstream so we are not a passive consumer, and track Multigres as a Citus replacement. Our moat is the shape layer and attach mode, which Azure does not have.
Incremental views are a crowded featurepg_trickle, Epsio, Feldera and others keep views fresh. Never sell shapes alone; sell the combination of SQL source of truth, MongoDB compatibility, cross-shard shapes and attach mode.
Data correctness bugs in shape maintenanceA wrong shape is silent data loss from the customer's point of view. The auditor, certificates and public Jepsen results exist for this reason. Fund them before general availability, not after.
Automatic shapes that cost more than they saveA proposer that creates shapes nobody reads adds write cost for nothing. Every proposal shows estimated cost and benefit, auto-accept is off by default, and unused shapes are flagged for removal after a quiet period.
Attach mode makes us look like another sync toolPrice and message attach as the first step of the database, not a product on its own. Every attach customer gets a cutover plan from the first week.
AGPL on Citus and pg_searchOffering modified AGPL components as a service means publishing those modifications. That fits open core if our new code stays separate. Confirm with a lawyer; ParadeDB's commercial license is a fallback.
MongoDB compatibility gapsDocumentDB does not cover every MongoDB operator. Publish a compatibility matrix, and position shapes as the main read path rather than a full drop-in Mongo replacement.
The word "shapes" is takenElectricSQL uses it for client sync. Decide early whether to keep it, or use a distinct term in public copy.
Write amplification from too many shapesEvery shape adds work to writes. Show per-shape write and embedding cost in the console, and let teams downgrade a shape from sync to bounded with one statement.
